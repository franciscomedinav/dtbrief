eBPF, Explained: The Small Programs That Run Inside the Linux Kernel

The Linux kernel used to be a no-go zone: change it and you risked crashing the whole machine. eBPF lets small, verified programs run inside it safely — and it is now the quiet engine behind cloud networking, security, and this week’s AI shields.

2014

The verifier

2 How it works: write, verify, load, run

Every eBPF program follows the same four steps:

1. Write — a developer writes a small program, usually in C or Rust, and compiles it to eBPF bytecode. 2. Verify — before anything loads, the kernel’s verifier statically checks every path the program could take. 3. Load — the program is compiled just in time to native machine code and attached to a hook point: a system call, a network event, a function entry. 4. Run — when the hooked event fires, the program runs to completion and writes its results into a shared store called a map, which a user-space program can read.

1WriteWrite the program in C or Rust and compile it to bytecode
2VerifyThe kernel verifier checks every path — safe, or rejected
3LoadThe program is JIT-compiled to native code and attached to a hook
4RunWhen the event fires, the program runs and writes results to a map

The verifier is the part that makes all of this possible. It rejects programs that could crash the kernel, dereference unchecked pointers, or loop forever — bounded loops were only allowed from kernel 5.3, and programs are capped at one million verified instructions. The check happens before the program ever runs, so a bad program never gets near the kernel. That is the difference between eBPF and the old way of extending the kernel, which was to load a module and hope.

The name is a leftover. Classic BPF, the Berkeley Packet Filter, was a tiny virtual machine from a 1993 paper by Steven McCanne and Van Jacobson, built to filter network packets for tcpdump. The extended version, led by Alexei Starovoitov and Daniel Borkmann, generalized it into a programmable runtime for the whole kernel. It merged into Linux 3.18 in 2014, and it is now stewarded by the eBPF Foundation, formed under the Linux Foundation in 2021 by Google, Meta, Microsoft, Netflix, and Isovalent.

1 What it is

eBPF, short for extended Berkeley Packet Filter, is a way to run small programs inside the Linux kernel — safely, and without changing the kernel itself.

The kernel is the layer between your applications and the hardware. It decides what runs on the processor, moves network packets, and hands out files and memory. Historically, if you wanted the kernel to do something new, you had to modify its source code or load a kernel module — and a bug in either could crash the entire machine. So most people simply did not touch it.

eBPF changes that bargain. It is a lightweight, sandboxed virtual machine that lives inside the kernel. You write a small program, the kernel checks it for safety, and then it runs at near-native speed whenever a chosen event happens — a packet arriving, a file opening, a system call firing. No reboot, no recompiled kernel, no module. That is why it now powers networking, observability, and security across the cloud.

3 eBPF vs a kernel module

A kernel module is a chunk of code loaded directly into the kernel, with full privileges and almost no safety net. It can do anything — including crashing the system with a single bad pointer. It also has to be built for a specific kernel version, and loading one usually means trusting its author completely.

An eBPF program is the opposite bargain. It runs in a sandbox, it is checked before it loads, it cannot crash the kernel, and it can be loaded and unloaded on a running system. The trade-off is that it is limited: it cannot do everything a module can, its programs are small, and it needs a reasonably modern kernel. For most jobs — watching, filtering, counting, blocking — the limits do not matter, and the safety is worth it.

Kernel moduleFull kernel privileges, no safety checks. A bug can crash the machine; built for one kernel version; loaded on trust.
eBPF programSandboxed and verified before it loads. Cannot crash the kernel; loads and unloads live; small programs, near-native speed.
A kernel module is trusted code with no safety net. An eBPF program is checked code in a sandbox — and that is the whole point.

4 Why everyone’s building on it now

Three stories in today’s briefing are the same story. Cisco and OpenAI launched Shirudo, an open source project that lets AI agents write eBPF shields — temporary protections that block a vulnerability inside the kernel while teams prepare a real patch. In a test, a shield written by OpenAI’s Codex blocked a Java4Shell exploit against a running service, and the service stayed online. Shirudo is a rewrite of Tetragon, the open source eBPF security platform from Isovalent, which Cisco acquired in 2024.

That is only the newest use. Cilium, the Kubernetes networking project built on eBPF, graduated from the Cloud Native Computing Foundation and became the default networking layer for Amazon’s EKS clusters in 2025 — the largest cloud vendor’s endorsement that eBPF is now mainstream. Observability tools use it to capture HTTP requests, database queries, and DNS lookups without changing a line of application code. And security tools like Tetragon and Falco hook directly at the kernel layer, so they can block a suspicious action the moment it happens, instead of reading a log after the fact.

The bet is simple. The kernel sees everything — every packet, every file, every process — and eBPF is the first safe way to program what it does with what it sees.

5 The honest part

Here is the catch. eBPF is Linux only, and the newest features need a modern kernel — many advanced uses want kernel 5.8 or later. Programs need privileged access to load, which means whoever can load them holds real power over the machine. Encrypted traffic stays opaque unless you hook the TLS library itself, so it complements application-level tracing rather than replacing it. And enforcement is a sharp tool: a wrong rule can stop a legitimate workload, which is why teams usually start with detection only and switch on blocking for a small set of proven rules.

There is also a trust question at the heart of this week’s news. Shirudo lets AI agents write kernel-level shields — and its answer is that every shield is cryptographically signed, verified before it runs, and recorded by a hardware chip. The verifier that made eBPF safe for humans is now doing the same job for agents. Whether that is enough is the question the security community will spend the next year answering.

Key terms

  • eBPF Extended Berkeley Packet Filter: a sandbox in the Linux kernel that runs small, verified programs at kernel events.
  • Kernel The core of the operating system, between applications and hardware. It schedules work, moves packets, and hands out files and memory.
  • Verifier The in-kernel checker that statically analyzes an eBPF program and rejects it if it could crash, hang, or corrupt memory.
  • Hook A point in the kernel where an eBPF program attaches and runs when an event fires: a system call, a packet arrival, a function entry.
  • Map An efficient key/value store in kernel space where eBPF programs write results for user-space programs to read.
  • XDP eXpress Data Path: an eBPF hook that processes network packets at the earliest possible point, before the kernel’s networking stack.
